# Synthetic cases

Every case in this directory is made up. The account ids, instance ids, keys and addresses are the
documentation placeholders AWS and the RFCs reserve for examples (111122223333, 444455556666,
ASIA-EXAMPLE-..., 203.0.113.0/24, 198.51.100.0/24, .example domains). The `model_output.json` files are
not a model's answers.

There are two kinds:

- **Gate cases**, typed by hand: `enrich-role-discovery`, `port-probe-ssh-open`, `port-probe-misread-port`
  and `root-login-misread`. Their answers are written to make the gate admit, refuse or downgrade in a
  known way, some wrong on purpose. When a deliberately wrong answer ends somewhere other than the right
  verdict, `label.json` says both: `verdict` is the right one, `replay_verdict` is where the gate takes the
  recorded answer. The two port-probe cases are contested: their group is described as a lab target,
  so `also_correct` lets a live model ask a person there without being marked wrong.
- **Verdict cases**, generated by `scripts/synth_cases.py` (don't edit their files; change the spec and
  run it again). Each has a reference answer the gate admits in full. They come in pairs where they can:
  an approved scanner scanning inside its range and the same scanner outside it; a CI user doing its job
  and the same user creating an admin.

So nothing measured with the recorded answers is a statement about any model's accuracy. They prove the
pipeline: evidence lands as records, claims bind or are refused, the verdict policy downgrades what it
should, and the write-back request has the right shape. `hubtriage eval --judge env` asks a real model
instead, and scores it against each label's `verdict` (or `also_correct`). It reports false benigns
first, then a table of label against verdict given: true_positive and needs_human both reach a person,
so mixing them up costs little, while a benign the label doesn't allow dismisses a real alert.

Cases recorded from a real account live beside this directory and say so in their `label.json`.
